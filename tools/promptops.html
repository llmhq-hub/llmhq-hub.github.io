PromptOps

Git blame for prompts. Find out which prompt caused the incident, in minutes rather than an afternoon.

Stable v0.6.0 Python 3.10+

Why PromptOps?

Your agent did something wrong in production last Tuesday. Which prompt was live at the time? What did it say before someone edited it? Which deploy shipped it?

If your prompts are string literals in code, or rows in a SaaS dashboard, those questions take an afternoon. PromptOps keeps prompts as YAML in your own git repo, so they get the same version history, blame, and diff every other artifact in your stack already has. No database, no vendor, no lock-in.

Features

Incident archaeology

promptops blame --at <timestamp> answers "what text was this prompt when the incident happened", from the deploy log and git history.

Production runtime, no SaaS

Ship one snapshot.json in your image. No .git/ directory and no git binary needed at runtime.

Semver impact on every change

promptops test diff grades a change MAJOR, MINOR or PATCH from the variable signature, so a breaking change cannot slip through review.

Version and deploy history

promptops history shows every version a prompt has been, and which deploys actually shipped each one.

One-command health check

promptops doctor checks structure, hooks, snapshot freshness, deploy-log health, versions and resolver mode.

Opt-in git hooks

Auto-version prompts on commit when you want it, graded by the same engine as test diff. init never writes to .git/hooks/ unless you ask.

Installation

terminal bash 
pip install llmhq-promptops

Quick Start

terminal bash 
# Create .promptops/ in your repo. Does NOT touch .git/hooks/.
promptops init repo

# Opt in to auto-versioning on commit (a deliberate second step)
promptops hooks install

# Scaffold a prompt template
promptops create prompt welcome-message

# Test uncommitted changes before you commit them
promptops test runtest --prompt welcome-message:unstaged

# Status of every prompt
promptops test status

Hooks have been opt-in since v0.4.0. init repo creates the directory tree and a default config, and never writes into .git/hooks/ unless you run hooks install (or pass --with-hooks).

Incident archaeology

The flow PromptOps exists for. Record what you ship, then ask what was live when something broke.

terminal bash 
# In CI, after you deploy
promptops deploy event --env prod

# Later, during an incident
promptops blame --at "2026-05-20T14:32:00Z" --prompt refund-policy
output text 
Blame: env=prod, at=2026-05-20T14:32:00+00:00

Deploy event:
  timestamp:   2026-05-20T14:20:58+00:00
  commit:      47d71643d7fe (47d71643d7fe9b4ef6e9391f8bb6d8c8b65150e2)
  deployed_by: ci
  metadata:    (none)

Resolved prompt 'refund-policy' (source=git):
  version: v1.2.0
  commit:  47d71643d7fe9b4ef6e9391f8bb6d8c8b65150e2
  text:
    metadata:
      id: refund-policy
      description: Refund decision policy
    template: |
      Approve refunds under {% raw %}{{ threshold }}{% endraw %} automatically.
      Escalate anything above to a human reviewer.

You now have the exact text that produced the behavior, and the commit it came from. Timestamps accept ISO 8601, a bare date, or the literal now. Drop --prompt to see every prompt at that deploy.

Then ask when it changed:

terminal bash 
promptops history refund-policy
output text 
📜 History for refund-policy
============================================================
  v1.2.0           47d71643  2026-05-20  Dev
      fix: escalate large refunds
      └─ deployed to prod at 2026-05-20T14:20:58+00:00 by ci

  v1.1.0           276fcb9a  2026-05-01  Dev
      feat: refund policy
      └─ deployed to prod at 2026-05-01T09:30:00+00:00 by ci

Deploy markers attach to the version that was live at that moment, not to whichever commit the deploy event happens to name. A deploy records the repository commit, which usually is not the commit that last touched this prompt.

Production runtime without git

Build a snapshot in CI, ship that one file, and resolve from it at runtime. The production image needs no .git/ directory and, since v0.5.0, no git binary either.

Dockerfile docker 
# In CI, before building:  promptops snapshot build
FROM python:3.11-slim
WORKDIR /app

RUN pip install --no-cache-dir 'llmhq-promptops>=0.6.0'

# The only PromptOps artifact. No .git/, no prompt YAML.
COPY snapshot.json /app/.promptops/snapshot.json
COPY app.py /app/

python:3.11-slim ships no git binary. Before v0.5.0 that made import llmhq_promptops fail outright; it now works, and promptops doctor runs cleanly in such an image. The distinction matters: the SDK's snapshot path needs neither the .git/ directory nor the git executable, while the CLI still needs git for any git-backed command.

Catch breaking changes at review

A prompt's variable interface is its contract with callers. PromptOps grades every change against it, and deliberately never grades prose: a rule that guessed at intent would produce annotations nobody trusts.

terminal bash 
promptops test diff refund-policy
output text 
IMPACT: MAJOR
  MAJOR required variable 'account_tier' added

--- working
+++ unstaged
@@ -12,3 +12,6 @@
   user_input:
     type: string
     required: true
+  account_tier:

Add --exit-code to gate CI on the verdict, or --json for tooling.

Exit codeMeaning
0NONE or PATCH
1the command failed
2MINOR
3MAJOR

This borrows git's --exit-code flag but not git's numbers. git diff uses 1 for "differences found", while PromptOps reserves 1 for "the command failed" because there are three severities to encode. Without the flag the command still exits 0, and prints a note telling you the flag exists so a forgotten flag cannot silently pass a breaking change.

Ready-made CI wiring ships in the repo: a GitHub Actions workflow that posts prompt impact as a sticky PR comment, and .pre-commit-hooks.yaml for teams already standardized on pre-commit.

Versions that bump themselves

With promptops hooks install done once, committing a prompt grades the change and writes the new version into the file. It is the same grader as test diff above, so a change your CI blocks as breaking cannot be stamped with a minor version.

terminal bash 
git commit -m "feat: tier-aware refund policy"
output text 
[promptops] 📊 Change analysis for .promptops/prompts/refund-policy.yaml:
[promptops]    Impact: MAJOR
[promptops]    Version: v1.2.0 → v2.0.0
[promptops]    • required variable 'account_tier' added
[promptops] ✅ Updated version to v2.0.0
[promptops] 🏷️  Created tag: prompt-refund-policy-v2.0.0

Impact comes from the prompt's variable signature and declared models. Prose is never graded, because the variable interface is the only part of a prompt with a caller-facing contract, and a rule that guessed at intent would produce annotations nobody trusts.

ChangeVersion
Required variable added, removed, renamed, or retypedMAJOR  1.2.0 → 2.0.0
Optional variable promoted to requiredMAJOR
Declared model removedMAJOR
Optional variable added or removedMINOR  1.2.0 → 1.3.0
Required variable relaxed to optionalMINOR
Model added, or an optional default changedMINOR
Prose changed, signature identicalPATCH  1.2.0 → 1.2.1
Nothing a caller depends on movedno bump

A brand-new prompt keeps the version you declared: there is nothing for a first commit to be backward incompatible with.

The bump rewrites the version line and nothing else, so comments and template: | formatting survive intact:

.promptops/prompts/refund-policy.yaml yaml 
# Owned by the billing team. Ping #billing before changing the wording.
metadata:
  id: refund-policy
  version: v2.0.0
template: |
  Explain the refund policy to {% raw %}{{ user_name }}{% endraw %} on the {% raw %}{{ account_tier }}{% endraw %} plan.

Tags are written as prompt-<id>-v<version>, which is the format promptops history and promptops blame read, so every version the hook creates is visible to the rest of the tool.

Upgrading? Hooks were broken from v0.2.0 through v0.5.0 and are repaired in v0.6.0. If you installed them on an earlier release and versioning never seemed to fire, that is why. See upgrading to v0.6.0.

Is this setup sane?

terminal bash 
promptops doctor

Six checks in one command: .promptops/ structure and config parse, hook installation, snapshot freshness against HEAD, deploy-log health including malformed lines, prompts with no committed version, and which backend the resolver will pick here. Exits 0 when every check is OK or a warning, and 1 when any fails, so warnings never break CI. Add --json for machine output.

Python SDK

app.py python 
from llmhq_promptops import get_prompt

# Smart default: snapshot in production, git in development
prompt = get_prompt("user-onboarding")

# Specific version references
prompt = get_prompt("user-onboarding:v1.2.1")
prompt = get_prompt("user-onboarding:unstaged")
prompt = get_prompt("user-onboarding:working")

# With variables
rendered = get_prompt("user-onboarding", {
    "user_name": "Alice",
    "plan": "Pro"
})

Failures raise PromptOpsError with a stable PROMPTOPS_E0XX code, a hint, and a link to the fix. Branch on e.code rather than parsing messages. Every code is documented in the error-code reference.

Framework Integration

Works with any LLM framework. Get a versioned prompt, pass it to your provider.

integrations.py python 
from llmhq_promptops import get_prompt

prompt_text = get_prompt("user-onboarding:working", {
    "user_name": "John",
    "plan": "Enterprise"
})

# Use with OpenAI
import openai
response = openai.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": prompt_text}]
)

# Use with Anthropic
import anthropic
client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-sonnet-4-5-20250929",
    messages=[{"role": "user", "content": prompt_text}]
)
